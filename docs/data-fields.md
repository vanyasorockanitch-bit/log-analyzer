# Карта данных и жизненный цикл

Документ описывает, какие данные проходят через Log Analyzer и как они меняются
на разных этапах обработки.

## Жизненный цикл файла

```text
uploaded -> format_detected -> parsed -> analyzed -> explained -> report_saved -> exported
```

Если формат не поддерживается или файл не удалось обработать, система должна остановить
дальнейшие шаги: статистику, NLP, отчёт и PDF нельзя строить по некорректным данным.

## Основные сущности

### Uploaded file

Загруженный пользователем файл.

Ключевые поля:

- `id` — внутренний идентификатор;
- `original_name` — исходное имя файла;
- `stored_path` — путь к сохранённой копии;
- `detected_format` — определённый формат лога;
- `status` — статус обработки;
- `created_at` — дата загрузки.

### Parsed event

Нормализованное событие, полученное после парсинга строки лога.

Ключевые поля:

- `id` — идентификатор события;
- `file_id` — связь с загруженным файлом;
- `timestamp` — время события, если найдено;
- `level` — уровень события;
- `source` — источник события;
- `message` — основное сообщение;
- `parsed_data` — специфичные поля конкретного формата.

Разделение на общие поля и `parsed_data` позволяет поддерживать разные форматы логов
без постоянного изменения основной схемы.

### Analysis result

Результат анализа по распарсенному файлу.

Ключевые поля:

- `id` — идентификатор анализа;
- `file_id` — связь с файлом;
- `total_events` — количество событий;
- `errors_count` — количество ошибок;
- `warnings_count` — количество предупреждений;
- `anomalies` — найденные аномалии;
- `created_at` — дата анализа.

### NLP explanation

Человекопонятное объяснение уникального сообщения.

Ключевые поля:

- `id` — идентификатор объяснения;
- `message_key` — ключ исходного сообщения;
- `original_message` — исходное сообщение;
- `explanation` — объяснение;
- `created_at` — дата создания.

Ключ сообщения нужен, чтобы не пересчитывать объяснение для одинаковых сообщений.

### Report

Сохранённый аналитический отчёт.

Ключевые поля:

- `id` или `report_id` — идентификатор отчёта;
- `file_id` — связь с файлом;
- `summary` — итоговое описание;
- `stats_snapshot` — снимок статистики;
- `anomalies_snapshot` — снимок аномалий;
- `nlp_snapshot` — снимок объяснений;
- `created_at` — дата создания отчёта.

PDF должен строиться по сохранённому отчёту, а не по временным данным в памяти.

## Почему такая модель удобна

- новые форматы логов добавляются отдельными парсерами;
- общая аналитика не зависит от конкретного формата;
- отчёты можно открывать повторно;
- PDF можно пересоздать по `report_id`;
- NLP-объяснения можно переиспользовать;
- переход с SQLite на PostgreSQL становится проще.

## Возможные улучшения

- добавить миграции Alembic;
- добавить строгие статусы обработки;
- добавить индексы по `file_id`, `timestamp`, `level`;
- добавить хранение исходных строк логов;
- добавить пользователей и роли;
- добавить политику удаления старых файлов и отчётов.
