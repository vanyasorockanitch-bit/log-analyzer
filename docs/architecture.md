# Архитектура Log Analyzer

Документ описывает архитектуру учебного backend-проекта Log Analyzer.

## Цель архитектуры

Проект должен показывать полный цикл работы с логами:

1. загрузка файла пользователем;
2. определение формата лога;
3. парсинг в нормализованные события;
4. сохранение данных;
5. расчёт статистики и аномалий;
6. AI/NLP-assisted объяснение сообщений;
7. сохранение аналитического отчёта;
8. экспорт отчёта в PDF.

## Общий поток данных

```text
Web UI
  -> FastAPI application
  -> upload router
  -> parser registry
  -> parser implementation
  -> normalized event model
  -> database
  -> stats/anomaly services
  -> NLP explanation service
  -> report service
  -> PDF export service
```

## Слои приложения

### 1. Web UI

Демонстрационный интерфейс позволяет загрузить лог-файл, запустить обработку,
посмотреть статистику, сформировать отчёт и скачать PDF.

### 2. API layer

FastAPI-приложение подключает отдельные роутеры:

- `upload` — загрузка файлов;
- `parse` — запуск парсинга;
- `stats` — статистика и аномалии;
- `nlp` — объяснение уникальных сообщений;
- `reports` — создание и получение отчётов;
- `export` — экспорт отчёта в PDF.

Такое разделение упрощает поддержку и показывает, какие части системы отвечают
за отдельные сценарии.

### 3. Parser registry

Parser registry нужен, чтобы добавлять новые форматы логов без переписывания
основной логики приложения.

Идея:

```text
file -> detect format -> choose parser -> parse lines -> normalized events
```

Каждый новый формат должен добавляться отдельным парсером с единым интерфейсом.

### 4. Data layer

Данные сохраняются в базе через SQLAlchemy. Для демонстрационной версии используется
SQLite, но архитектура подготовлена к переходу на PostgreSQL.

Основные группы данных:

- загруженные файлы;
- распарсенные события;
- результаты анализа;
- NLP-объяснения;
- сохранённые отчёты.

### 5. Analysis layer

Слой анализа рассчитывает статистику только по успешно распарсенному файлу.
Это защищает приложение от некорректных сценариев, когда отчёт строится по пустым
или временным данным.

### 6. NLP layer

NLP-модуль используется для получения человекопонятных объяснений уникальных сообщений.
В демонстрационной версии модель хранится локально, чтобы проект не зависел от внешних API.

### 7. Report/export layer

Отчёт сохраняется в базе и получает `report_id`. PDF строится не из временного состояния
интерфейса, а по сохранённому отчёту. Это делает сценарий повторяемым и более надёжным.

## Почему это важно для демонстрации

Проект показывает не только отдельный скрипт для парсинга логов, а полноценный backend-сценарий:

- есть API;
- есть хранение данных;
- есть разделение ответственности между модулями;
- есть обработка ошибок;
- есть отчётность;
- есть подготовка к расширению;
- есть тестовый сценарий.

## Точки масштабирования

Возможные направления развития:

- PostgreSQL вместо SQLite;
- Docker и docker-compose;
- очередь задач для тяжёлой обработки логов;
- потоковая обработка логов;
- поддержка новых форматов;
- авторизация и роли;
- хранение больших файлов в объектном хранилище;
- интеграция с observability-стеком: OpenTelemetry, Grafana, Loki;
- CI-проверка тестов при каждом push.
