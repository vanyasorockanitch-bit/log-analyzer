# Тестирование проекта

Эта папка содержит автоматические тесты для проверки основных сценариев Log Analyzer.
Приложение может работать и без этих файлов, но для ВКР они полезны: по ним видно,
что парсеры, API, сохранение результатов и PDF проверяются воспроизводимо.

## Как запускать

Все проверки запускаются из корня проекта и только через `.venv`:

```bat
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Чтобы после запуска не появлялись папки `__pycache__`, можно добавить переменную:

```bat
set PYTHONDONTWRITEBYTECODE=1
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Успешный результат выглядит так:

```text
Ran 10 tests in ...
OK
```

Во время PDF-проверки библиотека работы со шрифтами может вывести предупреждение
`MERG NOT subset; don't know how to subset; dropped`. Это не ошибка теста: если в
конце написано `OK`, значит тесты прошли.

## Что проверяют файлы

`test_parsers.py` проверяет парсеры и автоопределение форматов:

- Apache error log определяется как `apache_error`;
- Nginx access log определяется как `nginx_access`;
- неподдерживаемые строки получают формат `unknown`;
- одна строка Apache error log разбирается в нормализованное событие;
- одна строка Nginx access log разбирается в IP, HTTP-метод, путь, статус и сообщение;
- основные демонстрационные файлы `logs/samples/Apache_2k.log` и `logs/samples/access.log`
  действительно распознаются registry парсеров.

`test_api_flow.py` проверяет полный серверный сценарий через FastAPI `TestClient`:

- загрузка файла через `/upload/`;
- автоматическое определение формата и парсинг;
- получение статистики через `/stats/file/{id}`;
- получение аномалий через `/anomalies/file/{id}`;
- запуск NLP-суммаризации;
- сохранение объяснений сообщений в БД;
- генерация отчета через `/reports/generate`;
- получение отчета из истории;
- скачивание PDF по сохраненному `report_id`;
- блокировка анализа для файла со статусом `failed`;
- раздельная очистка загрузок и отчетов.

`test_support.py` содержит вспомогательную загрузку приложения с временной SQLite-БД.
Это важно: тесты не трогают рабочий `dev.db`, который используется при ручной
демонстрации приложения.

`__init__.py` нужен Python, чтобы папка `tests` корректно импортировалась как пакет.

## Как запускать отдельные проверки

Проверить только парсеры:

```bat
.\.venv\Scripts\python.exe -m unittest tests.test_parsers -v
```

Проверить только API-сценарии:

```bat
.\.venv\Scripts\python.exe -m unittest tests.test_api_flow -v
```

Запустить один конкретный тест:

```bat
.\.venv\Scripts\python.exe -m unittest tests.test_api_flow.ApiFlowTests.test_end_to_end_flow_persists_all_major_results -v
```

## Какие тестовые логи используются

Основные демонстрационные файлы лежат в `logs/samples`:

- `Apache_2k.log` — основной пример Apache error log;
- `access.log` — основной пример Nginx access log;
- `apache_error_sample.log` — маленький пример Apache error log для быстрой ручной проверки;
- `nginx_access_sample.log` — маленький пример Nginx access log для быстрой ручной проверки;
- `unsupported_sample.log` — пример неподдерживаемого формата.

В автоматических тестах большие файлы читаются только частично: тест берёт первые
строки, чтобы быстро проверить определение формата и не замедлять запуск.

## Как описать это в ВКР

В главе о тестировании можно указать, что использовались:

- unit-тесты парсеров Apache error log и Nginx access log;
- тесты автоопределения формата через registry парсеров;
- интеграционный API-тест полного сценария от загрузки файла до PDF;
- проверка защитного сценария, когда неподдерживаемый файл нельзя анализировать;
- проверка сохранения результатов анализа, NLP-объяснений и отчетов в БД.
