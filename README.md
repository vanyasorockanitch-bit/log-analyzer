# Log Analyzer

Веб-приложение для сбора, хранения, анализа журналов событий и формирования
аналитических отчётов. Проект развивается как дипломная работа, поэтому код,
структура каталогов и документация сделаны так, чтобы по ним можно было
объяснить архитектуру, поток данных и точки масштабирования.

## Запуск

Проект запускается только через виртуальное окружение:

```bat
run_dev.bat
```

Скрипт использует `.venv\Scripts\python.exe`, поэтому зависимости, локальная
NLP-модель и настройки среды остаются внутри проекта.

После запуска приложение доступно по адресу:

```text
http://127.0.0.1:7000
```

## Тесты

Тесты запускаются через встроенный `unittest` и отдельную временную SQLite-базу,
поэтому не трогают рабочую демонстрационную БД:

```bat
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

## Основной сценарий

1. Пользователь загружает лог-файл.
2. Система определяет формат через registry парсеров.
3. Файл автоматически парсится в нормализованные события.
4. Статистика и аномалии строятся только по распарсенному файлу.
5. NLP-модуль сохраняет объяснения уникальных сообщений в БД.
6. Отчёт сохраняется в БД и остаётся доступным по `report_id`.
7. PDF строится по сохранённому отчёту, а не по временным данным в памяти.

Если файл не распарсен, статистика, NLP, отчёт и PDF блокируются на уровне API.

## Тестовые логи

Готовые файлы для демонстрации лежат в [logs/samples](logs/samples):

- `Apache_2k.log` — основной пример Apache error log для демонстрации и тестирования;
- `access.log` — основной пример Nginx access log для демонстрации и тестирования;
- `apache_error_sample.log` — маленький быстрый пример Apache error log;
- `nginx_access_sample.log` — маленький быстрый пример Nginx access log;
- `unsupported_sample.log` — пример неподдерживаемого формата для сценария `failed parse`.

Сначала лучше использовать основные файлы `Apache_2k.log` и `access.log`: они
ближе к реальному объёму данных и лучше показывают статистику, аномалии и
человекопонятный отчёт. Маленькие файлы удобны для быстрой проверки парсера.

## Масштабируемость

Система уже подготовлена к расширению по нескольким направлениям:

- новый формат логов добавляется отдельным парсером с единым интерфейсом;
- общие поля события хранятся в `parsed_events`, а специфичные детали — в `parsed_data`;
- статистика и аномалии сохраняются в `analysis_results`;
- отчёты сохраняют снимок результата в `reports`;
- NLP-модель лежит локально в `.venv/models`, поэтому проект не зависит от внешних API;
- SQLite подходит для дипломной демонстрации, а SQLAlchemy упрощает переход на PostgreSQL.

## Что показать на защите

Для короткой демонстрации удобно идти по такой последовательности:

1. Загрузить `access.log`.
2. Показать, что файл автоматически получил формат и статус `parsed`.
3. Открыть статистику, временной ряд и аномалии.
4. Запустить суммаризацию сообщений.
5. Сгенерировать отчёт и открыть его в истории.
6. Скачать PDF по уже сохранённому `report_id`.
7. Отдельно загрузить `unsupported_sample.log` и показать защитный сценарий `failed parse`.
