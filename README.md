# Log Analyzer

Log Analyzer — учебный backend-проект и дипломная работа: веб-приложение для загрузки,
хранения, парсинга и анализа журналов событий с формированием аналитических отчётов.

Проект сделан как демонстрация навыков backend-разработки, работы с логами, базами данных,
API, отчётами и AI/NLP-assisted обработкой сообщений.

## Коротко для работодателя

- Направление: backend / Python / FastAPI / обработка данных.
- Формат: дипломный проект, подготовленный как portfolio project.
- Цель: показать полный поток данных от загрузки лог-файла до сохранённого отчёта.
- Основной сценарий: upload → parse → normalize → analyze → explain → report → export PDF.
- Проект развивался с использованием AI-assisted development: ИИ использовался как инструмент
  прототипирования, анализа решений, проверки идей и подготовки документации.

## Возможности

- загрузка лог-файлов через веб-интерфейс;
- определение формата логов через registry парсеров;
- парсинг Apache/Nginx-подобных логов в нормализованные события;
- сохранение событий и результатов анализа в базе данных;
- расчёт статистики и выявление аномалий;
- NLP/AI-assisted объяснение уникальных сообщений;
- сохранение отчётов по `report_id`;
- экспорт отчёта в PDF;
- healthcheck endpoint для проверки запуска API;
- отдельная тестовая SQLite-база для unit-тестов.

## Архитектура

Приложение запускается как FastAPI API и подключает отдельные роутеры для загрузки,
парсинга, статистики, NLP, отчётов и экспорта.

```text
Пользователь
  → Web UI
  → FastAPI
  → upload router
  → parser registry
  → normalized events
  → database
  → stats / anomalies / NLP
  → saved report
  → PDF export
```

Подробнее: [docs/architecture.md](docs/architecture.md)

## Структура данных

Основная идея — хранить общие поля событий отдельно от специфичных данных конкретного
формата лога. Это упрощает добавление новых парсеров и переход от демонстрационной SQLite-БД
к PostgreSQL.

Подробнее: [docs/data-fields.md](docs/data-fields.md)

## Запуск

Проект запускается через локальное виртуальное окружение:

```bat
run_dev.bat
```

Скрипт использует `.venv\Scripts\python.exe`, поэтому зависимости, локальная NLP-модель
и настройки среды остаются внутри проекта.

После запуска приложение доступно по адресу:

```text
http://127.0.0.1:7000
```

Проверка API:

```text
GET /api/health
```

## Установка зависимостей вручную

```bat
runtime\python.exe -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

## Тесты

Тесты запускаются через встроенный `unittest` и отдельную временную SQLite-базу,
поэтому не трогают рабочую демонстрационную БД:

```bat
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

## Основной сценарий

1. Пользователь загружает лог-файл.
2. Система определяет формат через registry парсеров.
3. Файл парсится в нормализованные события.
4. Статистика и аномалии строятся только по распарсенному файлу.
5. NLP-модуль сохраняет объяснения уникальных сообщений в БД.
6. Отчёт сохраняется в БД и остаётся доступным по `report_id`.
7. PDF строится по сохранённому отчёту, а не по временным данным в памяти.

Если файл не распарсен, статистика, NLP, отчёт и PDF блокируются на уровне API.

## Масштабируемость

Система подготовлена к расширению по нескольким направлениям:

- новый формат логов добавляется отдельным парсером с единым интерфейсом;
- общие поля события хранятся отдельно от специфичных деталей;
- статистика и аномалии сохраняются отдельно от исходного файла;
- отчёты сохраняют снимок результата;
- локальная NLP-модель позволяет не зависеть от внешних API;
- SQLite подходит для дипломной демонстрации, а SQLAlchemy упрощает переход на PostgreSQL;
- в будущем можно добавить потоковую обработку логов и очередь задач.
